## Execution protocol (both tiers)

1. Strict tranche order V1→V6; sub-tranche gates report progress % + E-invariants exercised, then → IMMEDIATELY proceed. Stopping after a green build without proceeding is a protocol violation.
2. Rip-and-replace: when a v1 construct is superseded, delete it in the same tranche. No dual paths, no compatibility shims (greenfield rule).
3. Zero suppressions: new `#[allow]` = gate failure. No `unwrap()`/`expect()` outside tests. Typed errors only in touched crates.
4. **Glossary conformance is a gate.** All new identifiers (types, fields, tables, columns, error variants, test names) must use V&S §2 terms with their bound meanings: `Instr`/cell never "token"; `Fibre` realizes token; `ControlStack`, `ConcurrencyTable`, `RecordId`, `Handle`, `Guard`, `Race`, `Barrier`, `Frame`. A CI grep-lint (V1.5) enforces the forbidden collisions (e.g. `Token` as a bytecode type, `Scope` naming the table).
5. Migrations numbered, ephemeral-PostgreSQL-tested in CI. Down paths documented; greenfield permits destructive downs.
6. Ignored-test count monotonically decreasing; any test a tranche makes runnable is un-ignored in that tranche.
7. **Substrate mismatch = halt.** If any tranche discovers the KERNEL-001 substrate does not match a plan assumption (missing API, different type shape, absent gate, unexpected behaviour), the executor HALTS and reports the mismatch verbatim. It NEVER adapts around it — no local reimplementation, no reinterpretation, no shims. Adaptive bridging of substrate gaps is the prohibited failure mode this rule exists for: a capable executor will produce a plausible bridge, and plausible bridges are how assumption drift becomes architecture drift. Every mismatch is dispositioned by Adam as either a plan amendment or a substrate fix before the tranche resumes.

**§13 amendment — parked-on-incident disposition for whole-instance-spanning guard rollback (landed 2026-07-22, resolves the "second finding" flagged above).** Root cause already documented in full in the entry immediately above (`apply_job_failure`'s `RollbackCaller::Dies` path, `bpmn-lite-kernel/src/lib.rs` ~2521) — not repeated here.

- **Adam's ruling (verbatim, the reasoning to preserve):** "§13 enumerated three dispositions for the triggering fibre and chose one: killed, not continued, not auto-respawned. It never considered parked. And parking is what fits: when rollback would empty the instance, don't kill the triggering fibre — restore the payload, pop the retiring guard from its control stack, park it at the GUARD> address on an incident. … The reframe: the rule was never 'never incident inside a guard' — it was 'the guard handles it instead of an incident.' When the guard's handling leaves the instance unrunnable, it hasn't handled anything, and the incident is the rule's boundary condition, not a violation of it. … Amendment: §13's kill-and-no-incident holds when the guard scope is a proper subset of live fibres. When it spans all of them, the triggering fibre survives, parked on an incident at the scope-open resume point."

**Part 2 — barrier-starvation investigation (Adam's hypothesis, investigated and CONFIRMED 2026-07-22; Ring 3 detection landed, remediation held for ruling).**

- **Hypothesis:** a `FORK` into N branches, one of which sits inside an interrupting `V2Guard` that fails and rolls back. Rollback kills only that branch's fibre (a proper subset of the instance — the zero-live-fibre Ring 3 assert stays quiet). `v2_reconcile_ancestor_membership` (called from `v2_rollback_guard_scope`) correctly deregisters the dead fibre from the fork's `ConcurrencyRecord.members` — but `Instr::V2Join` is the *only* code path anywhere that decrements `record.counters.count`, and only on a genuine arrival. A member that dies without arriving never arrives, so `count` never reflects its permanent absence — the barrier stays `Armed`, demanding an arrival that can now never come.
- **Confirmed by direct construction, not argument:** new test `fork_join_barrier_starves_when_a_member_dies_without_arriving_via_guard_rollback` — a 3-branch fork, branch A inside an interrupting guard, branches B and C each independently arrive at their own `V2Join` (both non-last, both park in `WaitState::V2Barrier`, `count` goes 3→2→1). Branch A's job then fails definitively; rollback kills branch A only (confirmed a proper-subset kill: no incident, matching the unmodified §13 disposition). Post-rollback, direct inspection of the materialized state confirms the exact stuck condition: the barrier record is still `Armed`, `counters.count == 1`, `members == {B, C}` (A correctly dropped), and *both* remaining members are already parked in `WaitState::V2Barrier` — i.e. every live member has already arrived, yet the record still demands one more arrival that can now never happen. `instance.state` stays `Running` throughout (2 live, non-terminal-waiting fibres) — confirmed invisible to the zero-live-fibre assert, which only fires on an empty fibre set.
- **Ring 3 detection landed (`ring3_shadow_check`, `bpmn-lite-kernel/src/lib.rs`, immediately after the `check_k_invariants` call):** for every post-transition `Armed` `RecordKind::Barrier` record, count how many of its live `members` have **not** yet arrived — "arrived" is cleanly checkable from present data: a live member is arrived iff its `fiber.wait == WaitState::V2Barrier{record_id}` for this exact record (the only state a barrier arrival ever parks in; the last arrival never stays `Armed` in a member-parked state at all, since it retires the record in the same transition). If the not-yet-arrived count is less than `counters.count`, the record can never reach zero — reject with `IntegrityError::Ring3Runtime`, message contains `"structurally unsatisfiable"`.
- **Red→green receipt:** the reproduction test was first run and passed with the *old* (pre-detection) assertions — `t5 = apply(..).unwrap()` succeeded, `barrier.state == Armed`, `barrier.counters.count == 1`, both members already arrived — genuinely stuck, not hypothetically, confirming the hypothesis before any fix landed. After adding the Ring 3 barrier check, the same `apply` call instead returns `Err(Integrity(Ring3Runtime("...structurally unsatisfiable...")))`; the test was updated to assert the rejection (matching the `Instr::End` remediation's own "GREEN because Ring 3 now rejects the bad frame" pattern) rather than leaving a permanently-red reproduction in the suite.
- **Held for ruling — remediation is an open fork, not decided here (per this task's explicit instruction not to invent a fix):** detection only. What should happen to a structurally dead barrier is undecided, and — mirroring §13's own three-vs-a-fourth-option framing — at least three shapes are visible from here, without a clear favourite:
  1. **Route to an incident**, symmetric with the §13 amendment above — the barrier's remaining live members get parked on a new incident (which fibre carries it, when there are ≥2 equally-implicated survivors, is itself unclear — unlike §13's single trigger fibre, a starved barrier has no fibre that "caused" the problem, only members that happen to be waiting).
  2. **Shrink the barrier's arity** to match reality — treat the dead member's absence as if it had never been forked in the first place, decrementing `counters.count`'s effective target so the remaining live arrivals can still satisfy it. This changes what the join "means" (fewer required arrivals than the program declared) and would need its own ratification — it's a semantic change to `V2Join`'s contract, not a bookkeeping fix.
  3. **Retire the barrier outright and cascade the cancellation** onward past the join, similar to how a `V2Guard`'s interrupting trigger cascades — but a `V2Join`'s "next" is a single fall-through address assuming a genuine winner reached it; retiring without a winner has no natural fibre to carry the continuation, the same gap option 1 has.
  None of these is implemented. Marked **held for ruling**, same as Q6 elsewhere in this doc.
- **Adam's side question — does v1 `Instr::Join`/`Instr::JoinDynamic` have the same exposure?** Checked independently (not assumed from the `Instr::End` sweep, which addressed a different question). **No, but for a more basic reason, not because it's protected:** v1 `Instr::Join`/`Instr::JoinDynamic` have no `ConcurrencyRecord`/membership mechanism at all — `join_arrive` is a bare integer counter (`snapshot.join_count`/`instance.join_expected`) against a static `expected` arity, with no `members` set to reconcile in the first place. v1 `Instr::Fork` (`bpmn-lite-kernel/src/lib.rs` ~1330) confirms this structurally: its children are built via plain `Fiber::new` with an empty `control_stack` — never pushed onto any `ConcurrencyRecord`, so `v2_cancel_guard_scope`'s subtree walk can never discover or cancel a v1-Fork child at all (it only walks control-stack/wait-state chains that reference D1 handles). This isn't "reconciled correctly" — there's no reconciliation happening because there's nothing for `v2_reconcile_ancestor_membership` to touch. A narrower, structurally different exposure remains possible in principle (a v1-Fork child that itself independently opens a `V2Guard` and is rolled back before reaching its own static `Instr::Join` would leave that join's hardcoded `expected` permanently unreachable) — but that is inherent to v1 Join's original design (no live-arrival tracking of any kind, for any reason a branch might not arrive), not a reconciliation gap this investigation's membership-vs-counter question is about, and mixing v1 `Fork` with v2 `V2Guard` inside one branch is not the routine topology. Not in scope for the Ring 3 check above (which is `RecordKind::Barrier`-only, i.e. v2 `V2Fork`/`V2Join` exclusively) and not fixed here.

- **Opcode-shape decision: a new, distinct instruction (`Instr::V2GuardArmTimer`, word `GUARD-TIMER>`), not an operand-encoding extension of `GUARD>`/`GUARD-N>`/`GUARD-R>`.** The V&S §8 placeholder ("current expectation is that it extends `GUARD>`'s existing operand encoding") is corrected in place, not merely fulfilled by coincidence — reading both candidate mechanisms in full before choosing (`Instr::V2Guard`'s kernel handler, `bpmn-lite-kernel/src/lib.rs` ~1811; `Instr::V2ArmTimer`'s, ~2071) settled it the other way. `V2ArmTimer` doesn't fold a trigger into `V2RaceOpen`'s own operand encoding either — it's a separate word that arms an *already-open* record via `fiber.control_stack.last()`, executed after the opener but before the scope's own body/close. Guards have the identical shape available: `V2Guard`/`V2GuardN`/`V2GuardR` open unconditionally with zero operands and the fibre keeps executing straight through into the guarded body, exactly like a race staying open between `RACE{` and `}RACE` while `ARM-*` words register alternatives. Folding a trigger into the guard-open words themselves would have meant either a sentinel/conditional operand (the guard's own stack effect depending on whether a trigger is present) or a second `Instr` field defaulting to "none" at every existing call site — the former is a stack-effect-by-flag anti-pattern the V&S already rejected once for interrupting-vs-not (`GUARD>`/`GUARD-N>`, distinct opcodes, not a bool) and once more for rollback-vs-not (`GUARD-R>`, a third opcode, not a flag on `GUARD>`); the latter would have touched every existing `V2Guard`/`V2GuardN`/`V2GuardR` construction site in the codebase (kernel `apply`, both verifiers, every hand-assembled fixture) for a feature most of them don't use. A standalone word touches none of that — a guard opened without it is byte-for-byte what it was before this ruling landed (proven by `v2_guard_opened_without_a_trigger_schedules_no_timer_effect`, below). Verifier-enforced adjacency (`v2_verifier.rs`'s new `Instr::V2GuardArmTimer` arm, ~line 550) requires it to sit at exactly `guard_open_address + 1` — "at guard-open time," matching the mechanics item's own wording, not merely "somewhere inside the guarded body." Applies uniformly to all three guard kinds, per the ruling's own "indifferent to disposition" text; see the `V2GuardR` finding below for the one place that uniformity needed a genuinely different *firing* mechanism, not a different *arming* one.
- **Mechanics — arm time.** `Instr::V2GuardArmTimer` (`bpmn-lite-kernel/src/lib.rs`, next to `V2GuardREnd`) pops a duration off the operand stack (T5/V2.7 addressing-review rider: a runtime-computed duration must be representable, same rationale as `V2ArmTimer`/`WAIT-FOR`), reads `fiber.control_stack.last()` for the record it arms, and emits `DurableEffect::ScheduleTimer` with a new `TimerKind::V2GuardTimer { record_id }` (`bpmn-lite-types/src/transition.rs`) — the same `EffectId::for_instruction(instance, fiber, pc)` deterministic derivation `V2ArmTimer`/`WAIT-FOR` already use (T5), reused verbatim, not re-derived. - **`V2GuardR`/timer-arming interaction — investigated and reported, per the brief's explicit ask, not silently assumed benign.** `GUARD-R>` carries no `handler` field by construction (A18: "its only unwind paths are `V2CancelScope` and automatic rollback-on-definitive-failure — never `V2TriggerGuard`, which requires a handler address"), so a timer-fired `V2GuardR` cannot go through `v2_trigger_guard_changes` at all — there's nothing to spawn. `apply_v2_guard_timer_rollback` (`bpmn-lite-kernel/src/lib.rs`, next to `v2_rollback_guard_scope`) runs the automatic-rollback path instead — the same `v2_rollback_guard_scope` primitive `apply_job_failure`'s definitive-`ContractViolation`-inside-an-interrupting-`GUARD-R>` branch already calls ("all roads lead to Rome," §13 amendment v0.5, now with a third caller). The one real adaptation: `apply_job_failure` always has a specific failing fibre (the one parked on the job that failed) to hand `RollbackCaller::Dies`; a guard's own deadline has no equivalent — nothing "failed," the scope simply timed out as a whole — so the representative fibre is the lowest-UUID live member of the record (deterministic, replay-stable; `v2_cancel_guard_scope`'s walk is exhaustive over the entire live subtree regardless of which member is named, so this choice is bookkeeping, not semantics). A second, genuine finding: V-10 forbids `GUARD-R>` from being *opened* while nested inside a `FORK`'s child fibre, but does not forbid a `FORK`/`JOIN` region from existing *inside* a `GUARD-R>`'s own extent (dominance, not exclusion) — so `guard_record.members` can legitimately span several live fibres across multiple fork branches when a timer fires, not just one. `v2_cancel_guard_scope`'s walk already handles that correctly (it discovers the whole live subtree, not just direct members) and the §13-amendment spanning-case check (does killing everything leave zero live fibres instance-wide) is computed over the full post-rollback fibre set, not just the chosen representative — so no V-10 amendment was needed, but the interaction was worth checking and is recorded rather than silently assumed clean.

- **The check that had to happen before writing any code.** Ruling H's ratified text (§5 `FORK n` row, §7 V-3, the ruling H body) claimed `V2Fork`'s operand-stack `n` becomes runtime-computed and V-3 weakens from equality to a bound. - **Hypothesis tested by construction, not argued in the abstract: CONFIRMED.** `V2Fork` needs no shape change at all. "Dynamic arity" is a compiler *lowering pattern* — the compiler always emits a `V2Fork` whose `targets` array has exactly the artifact-declared static maximum `n` (gateway out-degree, or MI's declared cap — ruling K); a branch that doesn't apply at runtime (false gateway condition, MI index past the actual collection length) is lowered to jump straight to the shared `V2Join` using only pre-existing opcodes (`BrIf`/`Jump`/`V2Join`) instead of doing its nominal work. That branch still executes a real `V2Join` arrival — indistinguishable, from the barrier's point of view, from a "real work" branch — so K-3's `count`/`arity` bookkeeping needs zero modification and `targets.len()` already **is** the static bound V-3 needs, not a separate quantity to compare against one. Proven, not asserted, by two fixtures:

**Post-close, not part of any prior tranche's sign-off — §18 v0.10 ruling I, item (e): boundary-timer and inclusive-gateway frontend lowering, XML and DSL (landed 2026-07-23).** Fifth of the six-step §18 implementation sequence (MI lowering, item (d), remains the last). - **The `LoweringTarget` fork, found before writing any lowering code, not after.** `bpmn-lite-engine/src/tests.rs`'s `T-IG-6` asserts `Instr::ForkInclusive`/`Instr::JoinDynamic` are LITERALLY present in `lower()`'s real output (via `engine.compile` → `Compiler::lower` → `lowering::lower`); `t_auth_6_boundary_timer_yaml` exercises `lowering::lower`'s v1 `race_plan` boundary-timer mechanism behaviourally via `bpmn_lite_authoring::publish::compile_program_from_dto` (confirmed by reading `publish.rs`: it calls `lowering::lower(&ir)` internally, not a separate pipeline). - **Zero-match/pre-fork mechanism: two new opcodes, not a flag on `V2Fork`, not a fat evaluate-and-branch instruction.** `V2Fork` has no condition-evaluation or zero-match capability of its own — deliberately, per ruling H ("a dumb 'always spawn N static targets' instruction"), and staying that way is exactly what keeps K-3/V-3 unchanged. So the zero-match decision — raise an Incident, never fork at all — must be made on the single forking fibre in ordinary straight-line code BEFORE `V2Fork` ever executes (there is no "spawn 0 and recover" outcome to unwind afterward once `V2Fork` commits). Investigated first, per the brief: `fail_contract` (`bpmn-lite-kernel/src/lib.rs`) is a private `fn` reachable only from inside an `Instr` match arm in `apply`'s own dispatch loop — there is no existing general-purpose "assert or incident" primitive callable from arbitrary straight-line bytecode, so this genuinely needed a new opcode, not a reuse. Two, in fact, both documented in `Instr`'s own doc comment (`bpmn-lite-types/src/types.rs`) with the same rigor as a ratified D2 word, since neither is one — they're V5-lowering-internal glue, not V&S vocabulary:
  - **`Instr::V2RouteZeroMatch`** — `( -- )`, unconditional. Reached only when a chain of `LoadFlag`/`V2LoadPlaceholderMatch` + `BrIf`-to-`V2Fork` checks all fall through (none matched); raises an Incident via `fail_contract`, same message shape and mechanism `RoutePayload`/`ForkPayload`/`ForkInclusive`'s own zero-match arms already use. No successors (`artifact::successors()`) and added to `v2_verifier::is_terminal`'s set — the same "static dead end, by design" class as `Fail`/`V2CancelScope`, not a new taxonomy; V-11 treats it as a legitimate terminal.
  - **`Instr::V2LoadPlaceholderMatch { placeholder, expected_value }`** — `( -- bool )`, DSL-only. A second, independently-motivated gap the same design surfaced: XML's inclusive-gateway conditions are already flag-based, so `LoadFlag` (an existing v1 primitive, already stack-effect-modeled) is reused as-is for XML's precheck and per-branch skip checks. The DSL's inclusive-split conditions are `(placeholder, expected_value)` string-equality checks (`instance.placeholder_matches`) with NO existing bytecode-level "load and check" primitive — `Instr::ForkPayload`'s v1 kernel handler evaluates them internally, never exposing an operand-stack-producing step. Without this word, the DSL side would need a structurally different (and asymmetric) lowering from XML's; with it, both frontends share one design.
  - Both wired through the full V2.7 checklist: `stack_effect`/`successors` (`artifact.rs`), `is_v2_instruction`, `is_terminal`/`arb_instr` proptest generator (`v2_verifier.rs`), kernel `apply` match arms (`bpmn-lite-kernel/src/lib.rs`, `V2LoadPlaceholderMatch` reuses `instance.placeholder_matches` + pushes `Value::Bool`; `V2RouteZeroMatch` calls `fail_contract` with a debug_map-derived message). No canonical-encoding/golden-bytes work owed (neither `Instr` nor its variants are in `canonical.rs`'s hash domain, confirmed by grep, same as every prior `Instr` addition this V5 sequence made).

- **The shape actually built (both frontends structurally identical, differing only in condition primitive):**
  ```text
  [precheck, OMITTED if any branch is always-live/default]
    LoadFlag(f1)/V2LoadPlaceholderMatch(p1,v1); BrIf(fork_addr)   -- per conditional
    ...                                                              branch, short-
    LoadFlag(fk)/V2LoadPlaceholderMatch(pk,vk); BrIf(fork_addr)      circuit OR
    V2RouteZeroMatch                            -- unreached if any branch matched
  fork_addr:
    V2Fork { targets: [h1..hn], pairing: fork_addr }
  h_i (conditional):  LoadFlag/V2LoadPlaceholderMatch; BrIfNot(join_addr); Jump(t_i)
  h_i (always-live):  Jump(t_i)
  join_addr:
    V2Join { pairing: fork_addr }; Jump(next)
  ```
  `fork_addr` is NOT always the gateway node's own base address — it's `base + precheck_len`, a real bug caught by a failing test before landing (`V2Join`'s `pairing` computed from the wrong address, `left: 0, right: 1` on the join-count assertion) and fixed by computing `precheck_len` once (`lowering::inclusive_precheck_len`/`dsl::frontend::dsl_inclusive_precheck_len`) and sharing it between the sizing pass, the fork/join pairing pre-pass, and emission — not re-derived three times, three chances to drift.

- **Default-branch handling — not dropped, and DSL/XML converge on the identical concept.** `ForkInclusive`'s v1 `default_target: Option<Addr>` (a true "if nothing else matched" fallback) has no XML equivalent to preserve: XML's `IREdge` carries the same `Option<ConditionExpr>` an XOR gateway's default edge uses, so "no condition" is XML's ONLY expressible default concept, and it already means "always taken, unconditionally" (v1's own `InclusiveBranch::condition_flag: None` — "always taken" — convention, unchanged). DSL's `routes()`-derived `default_target` (a `(None, None)` flow) is structurally the SAME shape. Both are modeled as one concept, "always-live," in the v2 lowering: an always-live branch's `V2Fork` header is a bare `Jump` (no check, never skips), and — the actual answer to "handling," not just "not dropped" — its mere existence makes the fork's target set provably non-empty, so the zero-match precheck is OMITTED ENTIRELY (dead code would otherwise never fire). Proven both ways: `lowering::tests::test_inclusive_gateway_lowering_v2_with_always_live_branch_omits_precheck` (XML), `dsl::frontend::tests::dsl_inclusive_split_with_default_flow_omits_zero_match_precheck` (DSL), and end-to-end via the real engine, `bpmn-lite-engine::tests::t_ig_v2_zero_match_with_default_runs_default_branch`.

- **Boundary-timer lowering's exact shape (XML only).** The host task (`ServiceTask`/`FfiServiceTask`) is wrapped: `V2Guard`/`V2GuardN` (interrupting per the BPMN boundary event's own flag) → `GUARD-TIMER>`'s arming pair (`PushI64(duration_ms)` + `V2GuardArmTimer`) → the task's own `ExecNative`/`ExecFfi` → the matching `V2GuardEnd`/`V2GuardNEnd` → the normal-path `Jump`. **A real ordering bug caught by the verifier before landing, not assumed correct:** `GUARD-TIMER>` must land at EXACTLY `guard_open_addr + 1` (verifier-enforced adjacency) — the first draft pushed `PushI64` AFTER the guard opened (between open and arm), which the verifier correctly rejected ("this instruction is not its immediate successor"); fixed by pushing the duration operand BEFORE the guard opens (`V2Guard`/`V2GuardN` touch neither stack, so the value survives across them untouched — the exact ordering `bpmn-lite-kernel`'s own `v2_guard_timer_trigger_fires_the_same_cascade_as_manual_v2_trigger_guard` fixture already used, that ordering wasn't re-derived from first principles until the failing test forced it). `TimerSpec::Date`/`Cycle` convert to a single relative duration (`timer_spec_duration_ms`, reusing the v1 `FfiServiceTask` arm's own `now()`-relative conversion for `Date`) — `GUARD-TIMER>` is one opcode, not two, unlike `TimerWait`'s `V2WaitFor`/`V2WaitUntil` pair, so there is no absolute-deadline arming word to lower `Date` to directly.
  - **A second, real finding, not glossed over: non-interrupting (`V2GuardN`) boundary timers require the escalation flow to close the inherited guard scope, not just the host task's normal-completion path.** `V2GuardN`'s handler-entry-state is POST-push (V4's own ratified derivation, `v4_nested_guardn_under_guard`-family kernel fixtures: the handler at address 7 closes with its OWN `V2GuardNEnd` before reaching `End`) — unlike `V2Guard`'s PRE-push handler, which needs no close since the scope was already retired at trigger time. V-1 (control-stack balance) therefore rejected the first non-interrupting fixture ("control stack not empty at program end") until the escalation terminal's own `End`/`EndTerminate` was made to close the scope too. Implemented as a targeted, honestly-scoped pre-pass (`guardn_close_before_end`, `lowering.rs`): walks the escalation flow's single-successor chain from the boundary event to its own terminal `End`, marking it to emit `V2GuardNEnd` first. **Deliberately narrow:** a branching escalation flow (a gateway, or a second nested boundary timer) is not resolved by this walk — it finds no terminal to mark, and `verify_v2_control_stack` then rejects the resulting program with a precise V-1 diagnostic rather than this function silently mis-lowering it. A linear escalation chain (the common shape) is fully supported.
  - Interrupting/non-interrupting distinction is the pre-existing BPMN `interrupting` flag on `IRNode::BoundaryTimer`, unchanged.

- **What's true for XML vs. DSL, and why.** Boundary timers: XML only, as scoped (DSL has no boundary-event AST surface — unchanged finding from V5.1). Inclusive gateways: both frontends, structurally identical shapes, differing only in the condition-evaluation primitive (`LoadFlag` for XML, the new `V2LoadPlaceholderMatch` for DSL) — neither frontend's lowering is "trivially derived from the other's" in the sense of one calling into the other's code (they're independent implementations, `lowering::lower_inclusive_diverging_v2` and `dsl::frontend::lower_dsl_inclusive_diverging_v2`), but they share one design, documented once and cross-referenced from both doc comments rather than duplicated. The `LoweringTarget` gate exists only on the XML side (boundary timers and inclusive gateways together, since both route through `lowering::lower`); the DSL side has no gate at all, for `SplitMode::Inclusive` specifically, because nothing locks its v1 shape.

**Post-close, not part of any prior tranche's sign-off — §18 v0.10 ruling K, item (d): parallel multi-instance frontend lowering, XML only (landed 2026-07-23).** Sixth and last of the six-step §18 implementation sequence. Builds directly on item (a)/(c)'s confirmed finding (an MI activity's declared max is "nothing more than a `V2Fork` with that many targets, using the SAME skip-to-`V2Join` pattern for collection indices beyond the actual runtime length") and item (e)'s `LoweringTarget`/precheck conventions.

- **The real finding, checked before writing any lowering code, per the brief's own instruction not to assume.** "Each fibre needs to know its own ordinal and be able to index into a runtime collection value" — grepped across `bpmn-lite-types::Value`, `ffi_bindings::DataObjectType`/`PrimitiveType`, and `BindingSource`: this codebase has **no array/collection-valued representation at any layer** (`PrimitiveType` is `Bool`/`I64`/`F64`/`String` only; `BindingSource` is `Literal`/`FlagRef`/`DomainPayloadRef`, none array-indexable). Building one — a new `Value::Array`, JSON-path array indexing in `bpmn_lite_vm::json_path`, a new `BindingSource` shape — is a materially larger, separate feature than MI's own arity/skip scaffolding needs. **Scoped down, deliberately and visibly, not silently:** an MI activity's `inputCollection` is represented by its RUNTIME LENGTH ONLY (an `I64`-valued flag the workflow populates before the fork runs), reusing the exact `flag_name`-reference convention `ConditionExpr` already uses for XOR/inclusive-gateway conditions rather than inventing a second name-reference shape. This is enough to build and prove the arity-bound/skip mechanism ruling K actually asks for; per-element VALUE access into the inner activity's own task body is NOT built by this step and remains explicitly out of scope. **Flagged here as the fork the brief asked to be reported, not picked silently:** if a live runbook needs the inner activity to read `collection[i]`'s actual value (not just know whether `i` is in range), this landing does not provide it — that is a materially different, larger feature (real array-value support end to end), not a "which is more code" call.

- **Design hypothesis (brief's own text) verified before building, not assumed: CONFIRMED — MI's `V2Fork` should always fork, unlike a gateway's true zero-match.** A gateway's `V2Fork` has a real "don't fork at all" precondition (all conditions false, no default — ruling J's `V2RouteZeroMatch` precheck). MI has no such precondition: `V2Fork`'s `targets.len()` is always exactly `declared_max`, unconditionally — the artifact-declared cap, not a runtime-computed quantity. Consequence, exactly as the brief predicted: **empty collection falls out of the SAME skip-to-join mechanism with ZERO special-casing.** If the runtime length is 0, every one of the `n` synthesized branches' `V2MiIndexLive` check is false, every branch `BrIfNot`s straight to the shared `V2Join`, the barrier still retires normally (all `n` "arrived," just instantly), and execution continues past the join — no incident, no zero-match precheck, nothing borrowed from the gateway case at all. `Instr::V2MiArityCheck` (below) is therefore NOT a zero-match precheck analogue at all — it has a different job (bounding the top, not guarding against the bottom), which is exactly why ruling K item (c) insists empty-collection and zero-match must not be unified: they are not merely differently-named versions of the same check, they are two different checks answering two different questions.

- **The shape actually built — self-contained within ONE `IRNode`, unlike `GatewayInclusive`'s diverging/converging PAIR.** A gateway's branches are edges to already-existing downstream graph nodes, needing a cross-node fork/join pairing stack (`inclusive_pairing_stack`, `lower_with_target`). MI is architecturally simpler: `IRNode::MultiInstance` has exactly one incoming and one outgoing sequence flow, and its `declared_max` branches are bytecode SYNTHESIZED internal to this one node's own instruction block — no pairing stack needed, no separate converging node in the graph at all.
  ```text
  base:
    V2MiArityCheck { length_flag, max: declared_max }   -- hard reject if actual > declared_max
    V2Fork { targets: [h_0..h_{n-1}], pairing: base+1 }
  h_i:  V2MiIndexLive { length_flag, index: i }
        BrIfNot(join_addr)
        ExecNative { task_type }             -- the inner activity's own work
        Jump(join_addr)
  join_addr:
    V2Join { pairing: base+1 }
    Jump(next)
  ```
  Per-node instruction count: `1 (arity check) + 1 (fork) + declared_max * 4 (index-live + BrIfNot + ExecNative + Jump per branch) + 1 (join) + 1 (trailing jump)`. `lower_multi_instance_v2` (`bpmn-lite-compiler/src/lowering.rs`) is the single new lowering function; `instr_count_for`'s `IRNode::MultiInstance` sizing arm computes the identical formula, shared rather than re-derived (the same "compute the formula once, share it" discipline item (e)'s `inclusive_precheck_len` established).

It carries `max_fires` as a static embedded field (verify-time-checkable, like `V2RaceOpen`'s `arm_count`), not a runtime-computed operand-stack value. `max_fires == 0` is rejected at verify time ("a cycle that never fires once is not a cycle").
  - **Mechanics.** `Instr::V2GuardArmTimer`'s kernel handler (`bpmn-lite-kernel/src/lib.rs:2051`) now looks up the record it's arming (checking `changes.concurrency_mutations` first, since `V2GuardN`/`V2GuardArmTimer` are verifier-enforced adjacent — the record is typically brand new in THIS same tick, not yet materialized into `snapshot`; falling back to `snapshot.concurrency_table()` for the re-arm-after-a-later-tick case) and, only for a `GUARD-N>`-kind (`RecordKind::Guard { interrupting: false }`) target, attaches an UNBOUNDED default repeat spec (`TimerRepeatSpec::new(duration, u32::MAX, 0)`) — ruling A's own "nothing expresses a non-re-arming variant" made concrete. `Instr::V2GuardTimerCycle`'s own handler patches that just-pushed effect's `repeat_spec` in place (guaranteed to be `changes.effects`'s last element, by the same adjacency the verifier enforces), narrowing `remaining` from `u32::MAX` down to `max_fires`. At fire time, `apply_timer`'s `TimerKind::V2GuardTimer` arm (`bpmn-lite-kernel/src/lib.rs`) now computes `rearm = (!interrupting).then(...).filter(|spec| spec.remaining() > 1).map(|spec| TimerMutation::Rearm { .. remaining - 1, fired_count + 1 })`, pushing `Rearm` (same `timer_id`, `due_at = fired_at + interval_ms`) when a re-arm is due, falling back to the pre-existing `TimerMutation::Consume` otherwise — `GUARD>`/`GUARD-R>` always `Consume` (their record retired above, nothing to re-arm against), matching ruling I's original fire-once behaviour byte-for-byte. Two stale doc comments claiming "a guard-arming timer never rearms" / "neither `TimerKind::V2Race` nor `TimerKind::V2GuardTimer` ever rearms" were corrected in place, per the brief's explicit instruction not to leave them standing.
  - **Exhaustion — "reverts to job," precisely.** The deleted `t_ni_3_cycle_exhausted_reverts_to_job` asserted the v1 host fibre (diverted into `WaitState::Race` for the cycle's duration) reverted to plain `WaitState::Job` once exhausted. The v2 mechanism has no equivalent diversion to revert FROM: arming/firing a guard timer never touches the guarded body's own fibre at all (`V2GuardN`'s own doc comment — "the guarded body keeps executing normally after arming"), so the host fibre is in `WaitState::Job` continuously, before, during, and after every fire, exhausted or not. The restored test asserts exactly this — the v2 shape of "reverts to job" is "was never not there" — confirmed against the boundary-timer semantics the brief asked to check, not approximated.

**Post-close, not part of any prior tranche's sign-off — §18 v0.10 ruling K Part 2: `Value::Array` + MI per-element value access (landed 2026-07-23, CAREFUL tier, blind-reviewed separately).** Closes the gap the item-(d) MI-frontend-lowering entry above explicitly flagged and did not build: "if a live runbook needs the inner activity to read `collection[i]`'s actual value... this landing does not provide it — that is a materially different, larger feature." Adam's own framing of why this is the second half of the same feature, not a follow-on: *"'Do this N times' isn't multi-instance; it's a loop. [The motivating] director example needs `collection[i]` — each signature request goes to a specific director. - **Part 1 — `Value::Array`, the container-shape decision.** `bpmn-lite-types/src/types.rs`'s `Value` enum gains `Array(Vec<Value>)`, tag `0x04` in `canonical.rs`'s `CanonicalEncode` impl. `Vec`, not `Box<[Value]>` (`V2Fork`'s `targets` precedent) — deliberately: `targets` is compiler-frozen once and never mutated at runtime, the right shape for "no spare capacity, immutable after construction." A `Value::Array` is the opposite — runtime-constructed data (populated via `orch_flags` at spawn/resume, or `StoreFlag` in-workflow), the same role every other entry in `flags: BTreeMap<FlagKey, Value>` already plays; `Vec` matches that convention (and `Fiber::stack`'s own shape), not `V2Fork`'s unrelated one.

- **Nesting — permitted, not forbidden, and this was a real choice, not an oversight.** A `Value::Array` may contain another `Value::Array`. The alternative (reject nesting) was considered and rejected: enforcing it would require either making `CanonicalEncode::canonical_encode` fallible (a ~15-impl, trait-wide blast radius `canonical.rs`'s own module doc comment explicitly scopes against — "every impl in this module is infallible by construction, by design") or an unenforced "authors just don't do that" convention — exactly the trap-door shape CLAUDE.md's working contract forbids ("enforce the mechanism, not a word"). Allowing nesting keeps the existing invariant intact and is fully tested (golden bytes + proptest, both a flat and a nested case) rather than an implicit assumption resting on nobody having built a nested case yet.

- **Size/depth bounding — the finding the brief asked to be checked for, and it was real.** Every other `Value` variant is fixed-width; `Array` is not, so `max_stack`/`max_registers` (slot-*count* bounds) stopped being sufficient the moment a single slot could hold an arbitrarily large/deep tree — a real, previously-free "frame size proportional to live tokens" guarantee (§2 glossary, "Frame") would otherwise have quietly acquired a hole. Two new constants, `types::MAX_VALUE_ARRAY_LEN = 4096` / `MAX_VALUE_ARRAY_DEPTH = 8`, enforced at both boundaries capable of introducing an oversized/deep array:
  - **`Value::canonical_decode`** — depth is checked mid-recursion (a new `array_depth: u32` field on `CanonicalReader`, incremented/checked BEFORE recursing into an `Array`'s elements, decremented after) — this is what actually bounds decoder stack depth against an adversarial-nesting input; checking only after a full (possibly stack-overflowing) decode would be too late for the depth bound's actual purpose. Two new `CanonicalDecodeError` variants (`ValueArrayTooDeep`/`ValueArrayTooLong`).
  - **`bpmn-lite-kernel`'s `validate_snapshot_limits`** — extended to walk every `Value` in `fiber.stack`, `fiber.regs`, and (new) `instance.flags`, rejecting via the existing `TransitionError::ResourceLimitExceeded` shape (same variant `verified_fiber_limit_is_enforced_before_interpretation` already proves for fiber count) if any exceeds the bound. This is also the boundary that (on the instance's first `apply` call after spawn/resume) catches an oversized/deep array supplied externally via `orch_flags` — **a residual gap, flagged rather than silently left:** there is no intake-time check at the `orch_flags`-seeding call site itself (`bpmn-lite-engine/src/engine.rs`'s `start`/`submit` paths), only at the next `apply()`. Fail-closed either way (the transition simply errors before any instruction runs), but a malformed spawn request is rejected one tick later than it could be, not immediately at the API boundary. Judged acceptable for this landing (matches the existing posture — no other resource limit, e.g. fiber count, is checked at intake either) but recorded for the reviewer, not silently accepted. **[CORRECTED 2026-07-23 — see the "gRPC-boundary orch_flags array-limit + Cancel/Terminate zombie-instance remediation" post-close entry below: an independent blind review found "fail-closed either way" understated the consequence — until the fix below landed, the fail-closed-one-tick-later path had NO recovery, `Cancel`/`Terminate` included, making an affected instance a permanent zombie, not merely a one-tick-delayed reject. The gRPC-boundary check is now added (closing new intake) and `Cancel`/`Terminate` are exempted from this specific check (closing the zombie path for anything already poisoned).]**

- **Part 2 — where the collection's actual data lives, the real architectural decision.** The prior item-(d) landing represented `inputCollection` as an `I64` LENGTH-only flag; two candidate homes for the real data were investigated, per the brief:
  - **`domain_payload`** (a JSON string, `ProcessInstance::domain_payload`) — rejected. Reading it would require inventing a `json_path`-style array-indexing mechanism that does not exist anywhere in this codebase today (checked, not assumed) — a second, parallel runtime-data-access convention alongside the one (`flags: BTreeMap<FlagKey, Value>`) that already exists and that MI's own length signal already used.
  - **A flag holding `Value::Array` directly** — chosen. `Instr::V2MiIndexLive`/`V2MiArityCheck`'s `length_flag: FlagKey` field is renamed `collection_flag: FlagKey` and now names a flag holding the collection's actual `Value::Array`; length is DERIVED via `.len()` (`mi_collection_len`, `bpmn-lite-kernel/src/lib.rs`), not tracked as a second, separately-settable `I64` alongside it. The two-flag design (one length, one data, kept manually in sync) was considered and rejected as a redundant-state footgun — nothing would catch the two silently disagreeing, exactly the shape CLAUDE.md's working contract rejects. Single source of truth, and the more natural fit with how flags are already used elsewhere in this codebase.
  - **BPMN XML shape unchanged.** `<zeebe:loopCharacteristics inputCollection="<flag-name>" maxInstances="<n>"/>` still just names one flag; only the runtime TYPE that flag is expected to hold changed (`Value::Array` instead of `Value::I64`). No parser/DTO/export_bpmn structural changes beyond the field rename (`bpmn-lite-compiler/src/{parser,ir,lowering}.rs`, `bpmn-lite-authoring/src/{dto,dto_to_ir,ir_to_dto,export_bpmn}.rs`).

- **Per-branch delivery mechanism — investigated, not assumed, and it surfaced a genuine finding about `ExecNative`.** The brief asked whether folding delivery into `V2MiIndexLive` itself (`( -- bool value )`) or a small parallel instruction was the better fit, and to read how `ExecNative` expects its inputs. Doing that reading surfaced a real finding: **`Instr::ExecNative`'s `argc` field is vestigial.** It looks, from its name and its `stack_effect` table entry (`artifact.rs`, `(argc, retc)`), like the natural place to wire an operand into a job — but `argc` is set to `0` at every call site in this codebase (grep-verified across service tasks, FFI tasks, and MI) and the kernel's `ExecNative` handler (`bpmn-lite-kernel/src/lib.rs`) destructures `{ task_type, retc, .. }` — it never reads `argc` and never pops any operand off `fiber.stack` before dispatching the job. What the external job actually receives is `orch_flags`, a snapshot of `instance.flags` taken at the moment `ExecNative` runs — the SAME pipeline every existing service task's inputs already flow through.

  Given that, wiring MI element delivery through `argc` would mean either teaching `ExecNative` to actually pop and forward operands (a change to a mechanism every service task in the codebase shares — well outside this landing's scope) or pushing a value nothing ever consumes (dead weight on the operand stack, and pointless since nothing downstream could read it either). Neither is right. **Chosen design:** `V2MiIndexLive` itself is UNCHANGED (`( -- bool )`) — folding value delivery into its own stack effect would have made it conditional on a runtime outcome a per-PC static stack-height verifier cannot see statically. A new, small, parallel instruction, **`Instr::V2MiLoadElement { collection_flag, index }` (`( -- value )`)**, runs only on the live path — immediately after `V2MiIndexLive` + `BrIfNot` has already filtered out the dead path — and is immediately followed by the PRE-EXISTING `Instr::StoreFlag`, popping the loaded element into a synthesized per-branch-UNIQUE flag (`<node_id>_mi_element_<i>`, interned by `lowering.rs`'s `lower_multi_instance_v2`). That flag then reaches the job through the existing `orch_flags` pipeline, unmodified. Composing two already-proven primitives (`V2MiLoadElement`, a `LoadFlag`-shaped producer; `StoreFlag`, unmodified) to route through an already-existing pipeline, rather than inventing a new delivery mechanism — the same "no shape change needed, compose what's proven" posture ruling H's dynamic-arity `FORK` work established.

  **Per-branch-unique flag keys, not one shared scratch key — a deliberate choice, reasoned through explicitly.** A single shared key would still be race-free in practice: one fibre's `StoreFlag`+`ExecNative` pair executes atomically within a single `apply()` transition (nothing else can interleave inside it), and `JobActivation.orch_flags` is a materialized CLONE at enqueue time, not a live reference — so even a reused key could not leak one branch's element into another's already-enqueued job. But that correctness argument depends on understanding the tick model's atomicity; a unique key per branch needs no such argument at all. The extra `declared_max` interned flag keys are cheap, so the design that doesn't require the reader to reconstruct a liveness argument was chosen.

  **`V2Fork` itself needed no shape change — reconfirmed, not merely assumed to still hold.** The synthesized per-branch instruction sequence grew from 4 to 6 instructions (`V2MiIndexLive, BrIfNot, V2MiLoadElement, StoreFlag, ExecNative, Jump`), which meant the compile-time branch-size arithmetic in TWO places in `lowering.rs` had to move together — `lower_multi_instance_v2`'s own address computation AND a separate, easy-to-miss node-size-precomputation table (`estimate_instr_count`'s sibling match, `IRNode::MultiInstance { declared_max, .. } => declared_max * 6 + 4`) used by the compiler's two-pass addressing scheme. Missing the second one produced a real, caught-by-the-test-suite bug (a stale `*4 + 4` size estimate caused every downstream node's address to be wrong, manifesting as a spurious "backward jump" verifier rejection) — recorded here because it is exactly the kind of "two independent declarations of the same fact" class of bug CLAUDE.md's "DAG is normative" principle warns about in the artifact-DAG context, found here in the compiler's own address bookkeeping instead.

- **`V2MiArityCheck`'s bound — count vs. total encoded size, cross-referenced not re-solved.** `V2MiArityCheck` still bounds element COUNT only (`length > max`); an over-large TOTAL encoded size (declared-max element count, but each element itself a large/nested `Value::Array`) is bounded separately and independently by Part 1's `MAX_VALUE_ARRAY_LEN`/`MAX_VALUE_ARRAY_DEPTH` plus `validate_snapshot_limits`'s new per-flag-value walk — not re-implemented a second time inside `V2MiArityCheck`, per the brief's own instruction to cross-reference rather than double-solve.
