  - **Round 2 — `lldb` attached to the live hung worker thread** (`dangerouslyDisableSandbox` required; sandboxed `process attach` hangs indefinitely with no diagnostic, not a finding about the target). The worker thread (not the main test thread, which is cleanly parked in `semaphore_timedwait_trap` via a channel `recv_timeout` — a real, idle wait) shows **stop reason `EXC_BAD_ACCESS (code=2)`** at `bpmn_lite_kernel::Changes::finish + 20`, called from `apply_tick:1355` (`return Ok(changes.finish(instance));`) from `apply` from `tick_instance_inner`'s async closure chain — a normal, shallow, four-frame call stack (`bt -c 5`), not runaway recursion. Disassembly at `$pc`:
    ```
    stp    x28, x27, [sp, #-0x20]!
    stp    x29, x30, [sp, #0x10]
    add    x29, sp, #0x10
    sub    x9, sp, #0x11, lsl #12      ; x9 = sp − 0x11000 (68KB target frame)
    sub    sp, sp, #0x1, lsl #12       ; sp -= one page
    -> str    xzr, [sp]                   ; <-- $pc: guard-page probe write
    cmp    sp, x9
    b.ne   <+16>                       ; loop until sp reaches x9
    ```
    This is the compiler-generated stack-probe loop LLVM emits for a function whose debug-build stack frame exceeds one page — `Changes::finish` needs ~68KB of stack in this unoptimized build (plausible for a function built almost entirely of by-value `Transition`/`Changes`/`ProcessInstance` locals across a dozen `for` loops with no optimization). `register read` showed `sp == 0x16dba7b20`, **identical to the fault address** — the very *first* probe of this loop already lands on the guard page: the thread's stack was already exhausted *before* this call, and this ordinary, shallow call was simply the one that finally needed more than the one page of slack left. `process continue` re-stopped **immediately, at the identical `$pc`, identical fault**; the next `process interrupt` errored `"Process is not running"` because it had *already* re-stopped on its own — the OS re-delivers the same fault the instant the instruction is retried, so there is no window where it's actually running. **`$pc` does not change across resume attempts — it cannot, by construction: the same store to the same guard page re-faults every time.** This is spin in name only; more precisely it is a deterministic, immediate re-fault, not a CPU-bound loop making any progress at all.

  - **Standing characterization, replacing BL-T13's retracted one:** CA-R1.5b's 20-second timeout is not a kernel compute hang and not (as far as this evidence goes) a cycle or zero-progress condition either — it is a **debug-build stack-exhaustion artifact** on the spawned worker thread that runs `tick_instance_inner` inside `Runtime::block_on`: whatever sits above this frame in that thread's call stack (the async-fn state machine, tokio's own frames, the surrounding test harness) has already consumed nearly the entire thread stack by the time an ordinary, shallow kernel call arrives; in an unoptimized build, `Changes::finish`'s unusually large debug-mode frame is what pushes it over, and the fault then re-triggers forever with no crash message and no forward progress — which is exactly what an external observer sees as a silent, unkillable-looking hang. Neither BL-T11's zero-progress check nor BL-T13's cycle detector could ever have addressed this: both are pure, in-process logic gated on committed transitions; this is a hardware fault that happens before any transition is ever built. Whether this same exhaustion pattern is reachable in corporate-actions-engine's own production (release) builds, or is specific to this debug-build reproducer's thread-stack budget, is unresolved and out of scope for this diagnostic-only pass — no fix attempted, per instruction.
