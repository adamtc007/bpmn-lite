No Incident was ever created — this is not the "fails fast with an Incidented" outcome the ruling named as one acceptable close, nor a clean pass; it is the timeout itself, which the ruling names as a failure. **New evidence, materially revises the picture:** a live `sample` capture during the hang shows ~76% of samples (2690/3539 on that call path) landing inside `tick_instance_inner`'s own closure chain → `bpmn_lite_kernel::apply` → `apply_tick` → `Changes::finish` → `TransitionBuilder::new` — sustained, real CPU-bound execution, not a lock wait and not a repeating no-op. - **BL-T13** (2026-09-17) — CA-R1.5b-drive-loop, amended ruling: replaced BL-T11 item 1's zero-progress-only detection with general per-run cycle detection in `tick_instance_inner`. After each committed transition, the resulting schedulable state is hashed (`PersistedSnapshotState::schedulable_state_hash()`, new — the same BLAKE3(canonical(...)) domain as Ring 2's `SnapshotEnvelope::state_hash()` but deliberately omitting `revision`/`artifact_hash`, the two fields that make Ring 2's own hash unique per commit by construction) against a per-run `HashMap` of every state already seen; a repeat ends the run Incidented (`ContractViolation`), naming the repeated hash, the two bracketing transition ids/revisions, and the cycle length. Zero progress is kept as the length-1 case (a fast-path short-circuit, not superseded — `tick_made_zero_progress` and its tests are unchanged). New in `bpmn-lite-types`: `Snapshot::to_persisted_state()` (reverse of the existing `to_runtime_snapshot()`) and `PersistedSnapshotState::schedulable_state_hash()`; the kernel's own pure `apply()`/`materialize_snapshot()` untouched, the latter reused as-is. Independent blind review found two real HIGH-severity gaps before landing, both fixed: a doc comment falsely claiming an end-to-end trigger test existed for a genuine length>1 cycle (it didn't — no such trigger is known to be constructible, since every id a legal program could mint is revision-derived and so can never repeat by construction; the doc comment now says this plainly), and a fuzz test whose own claimed coverage was false (it drove repetition via `tick_due_timers`, which routes through a completely separate single-shot commit path with no cycle ledger at all — confirmed empirically by the reviewer instrumenting both code paths: 0 hits on the claimed path, 91 on an unrelated one). Replaced with a `V2Fork`-based fuzz test (2-6 random branch widths per seed, through the real BPMN-XML compiler) that genuinely drives `tick_instance_inner`'s own outer loop through multiple within-one-call iterations across the same `seen` map — re-verified by the same instrumentation technique (178 hits on the intended path, 0 on the fast path). Commits: `e2295d2`, `44e712b` on `eop/ca-reuse-001`, **not pushed**.
