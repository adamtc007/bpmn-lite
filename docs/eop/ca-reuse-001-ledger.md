No Incident was ever created — this is not the "fails fast with an Incidented" outcome the ruling named as one acceptable close, nor a clean pass; it is the timeout itself, which the ruling names as a failure. **New evidence, materially revises the picture:** a live `sample` capture during the hang shows ~76% of samples (2690/3539 on that call path) landing inside `tick_instance_inner`'s own closure chain → `bpmn_lite_kernel::apply` → `apply_tick` → `Changes::finish` → `TransitionBuilder::new` — sustained, real CPU-bound execution, not a lock wait and not a repeating no-op. This disproves the zero-progress-stall theory for *this* observed hang: item 1's fix cannot fire because every tick in the loop is apparently making genuine (if individually tiny) progress; the loop is doing large amounts of real, bounded work, not spinning on nothing. The actual mechanism looks closer to finding-doc theory (a) ("10,000 genuinely bounded but real iterations taking far longer in wall-clock") than to a stall or a store-layer lock block — but *why* `tick_instance_inner` needs so many real iterations per `relay_due` call is unexplored; chasing that is new kernel work, out of this ruling's scope, not started.
